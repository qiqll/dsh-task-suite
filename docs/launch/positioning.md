# 产品定位与介绍口径

这份文档是市场条目、GitHub README、宣传落地页和社媒文案的唯一口径。改定位先改这里，再同步四处。

## 一句话

**把 Agent 从“助理”变成一支工程团队：主 Agent 只调度，后台 Agent 交付，机器验收后才算完成。**

英文：

**Turn one coding agent into a small engineering team: a lead agent schedules, background agents deliver, and machines verify before anything counts as done.**

## 30 秒版

现在的 coding agent 很聪明，但工作方式还是“助理”：你要盯着它、等它做完一件、它说完成你再去验。真正稀缺的不是模型能力，而是**管理能力**。

DSH 任务流水线把主 Agent 变成 Tech Lead：需求先进入任务池，拆成有验收标准的任务；每个任务交给独立上下文的 subagent 执行；交付后机器重跑测试、比对开工基线、审计测试是否被改弱；通过后进入待验证，由你最终确认归档。

你从“追着 Agent 跑的人”，变成“带团队交付的人”。

## 四换一底线

这是所有介绍的主骨架，顺序固定。

| # | 从 | 到 | 一句话解释 |
|---|---|---|---|
| 01 | 助理 | 团队 | 主 Agent 只做 Tech Lead：对话、拆解、调度、验收；具体工作由独立 subagent 完成。 |
| 02 | 对话 | 任务 | 每个需求都有 ID、优先级、验收标准、状态和依赖；按工程交付，而不是按聊天记录。 |
| 03 | 同步 | 异步 | 需求可以一次投递多条，进入任务池按序消化；你不必守着对话等它做完一件再提下一件。 |
| 04 | 黑盒 | 驾驶舱 | 任务、Agent、指标、事件流一屏可见；当前在做什么、什么卡住、什么待确认，一目了然。 |
| — | 自述 | 证据 | **底线**：worker 说“完成”不算完成；机器重跑测试、比对基线、审计测试改弱，人再做最后确认。 |

> 对外不要只讲“多 Agent”。多 Agent 是手段；真正的差异是**任务契约 + 机器验收 + 异步队列 + 可见性**。

## 三个结果

1. **你被解放出来**：不用和 Agent 保持同频，想到需求先投递，再回来看结果。
2. **交付可审计**：任务有状态、有基线、有验收证据；出问题能定位、能回滚。
3. **上下文更干净**：每个 worker 独立上下文，长任务不再污染主会话。

## 目标用户

- 同时推进多个任务的独立开发者
- 被 Agent“假完成”坑过、开始给 Agent 加测试的人
- 想让 AI 交付过程可审计的小团队
- 使用 DeepSeek Harness、愿意装插件的人

## 不适合

- 只想要简单 todo 列表的人
- 一次性脚本、不需要验收的个人项目
- 期待完全无人值守、自动合并上线的团队

## 边界与禁语

可以说：

- “主 Agent 只调度” → 在流水线模式下成立
- “机器验收” → 有测试命令的项目；没有测试的项目仍有人工确认和改动审计
- “异步” → 指需求投递与交互异步，不承诺所有任务并行执行
- “实时面板” → 5 秒轮询的近实时视图

不要写：

- “全自动开发 / 无人值守”
- “所有项目都能机器验收”
- “无限并行 / 多任务同时执行”
- 没有数据支撑的用户量、效率倍数、融资/大厂背书

## 钩子备选

- 别管 Agent 了，带团队。
- 一个 Agent 是助理，一支 Agent 团队才是产能。
- AI 说“做完了”，这次终于有人验收。
- 你缺的不是更强的模型，是更好的管理。
- 把需求扔进去，把结果拿回来。
